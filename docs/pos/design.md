# 店舗 POS 設計書（山口店）

作成日: 2026-10-31
状態: 全体像の草案。モックアップで流れを確かめ、「深める論点」を詰めてから実装に入る。

## 1. 目的と前提

山口県で実店舗の買取・販売店を開く。店頭での買取（査定〜本人確認〜現金払い）、買い取った商品の販売、在庫、レジ締めを 1 つの POS で扱う。

決定済みの前提（2026-10-31 時点）:

| 項目 | 決定 |
|---|---|
| 所在地 | 山口県（山口県青少年健全育成条例 10 条の対象） |
| 決済 | 現金のみ（買取の支払いも販売の受け取りも） |
| 本人確認 | 金額にかかわらず全件実施 |
| 在庫 | 販売もするので手持ち在庫を管理する |
| 買取価格 | 通販（quadra テナント）の価格表を取り込み、店舗で調整できる |
| 端末 | iPad（PWA）、レシートプリンタ、バーコードリーダー。キャッシュドロワーは使わない（既存の金庫から手で数えて渡す） |
| データの置き場所 | 東京・山口と同じ Supabase プロジェクト内に新テナントを作る（新プロジェクトは作らない） |
| URL | `yamaguchi-cardshop.kaitorisquare.com`（候補。印刷物を作る前に確定する） |
| 法人 | 店舗と通販は同じ法人。店舗→事務所の在庫移動は社内振替（売買ではない） |
| 人員 | 通販の検品と店舗業務を同じ人が兼ねる。開店時はテナントごとに 1 アカウントずつ持つ |
| 客向けの価格表示 | 電子棚札は使わない。ラベルに価格を印字せず、iPad の客向け表示か QR コードの価格ページで見せる |
| 価格同期 | 自動（毎日、時刻は設定）を基本にし、合わないときは手動で「今すぐ同期」 |

## 2. 全体構成

### 2.1 配置

- 同じリポジトリに `src/app/(pos)/pos/` ルートグループを追加する。別リポジトリ・別 Vercel プロジェクトにはしない。
- 店舗テナントのホストで `/pos` が POS、`/admin` が店舗の管理画面になる。テナント判定は既存の `src/lib/tenant-slug.ts` のサブドメイン方式をそのまま使う。
- PWA 化（`src/app/manifest.ts` と Apple 用 meta）で iPad のホーム画面から全画面で起動する。オフライン動作は対象外（常時オンライン前提）。
- データは既存の RLS とテナント一致チェック（`src/lib/security.ts` の `requireRole`）で店舗テナントに閉じる。通販側のアカウントからは見えない。両方を見る人はアカウントを 2 つ持つ。

### 2.2 テナント設定の追加

`tenants` に次を追加する。

| 列 | 型 | 用途 |
|---|---|---|
| `mode` | `'online' \| 'store'` | 店舗テナントでは通販の公開ページ（申込フォーム、価格表、マイ注文）を出さず、`/` は `/pos` へ誘導する |
| `cash_only` | boolean | true なら振込先入力・振込系の UI を隠す |
| `price_source_tenant_id` | uuid null | 価格同期の取り込み元（quadra） |
| `store_price_rate` | numeric | 店舗の買取価格係数（例 0.95 = 通販の 95%） |
| `price_sync_time` | time null | 自動同期の時刻（null なら自動同期しない） |
| `invoice_registration_number` | text null | 販売レシートに載せる適格請求書発行事業者の登録番号（登録している場合） |
| `receipt_header` | jsonb | レシートに載せる店名・住所・電話・古物商許可番号、注意書き、ロゴ |
| `printer_address` | text null | レシートプリンタの IP アドレス（端末設定でも上書き可） |
| `high_value_approval_threshold` | integer null | この金額以上の買取は manager の承認を必須にする |
| `customer_price_display` | `'ipad' \| 'qr' \| 'none'` | 客向けの売価の見せ方（iPad の客向け表示 / QR コードの価格ページ） |

これらは POS 内の「設定」タブ（manager / admin のみ）と管理画面の「店舗設定」の両方から変更できる。

### 2.3 権限

| 役割 | できること |
|---|---|
| staff | 受付、査定入力、本人確認の記録、申込書の署名、**現金支払いの記録**、**レジ締め**、販売、在庫参照、レジ開局、台帳の閲覧（2026-11-07 決定: 店舗は staff のアカウントで運用する） |
| manager | 上記に加え、取消、価格調整（店舗に manager は置かない想定） |
| admin（遠隔） | 上記に加え、スタッフ管理、設定、状態ランク表・価格帯の変更、台帳の CSV 出力、高額取引の確認 |

現金支払いの記録は既存の DB ガード（`guard_order_payment_method`、`record_order_payment`）が呼び出し元に admin / manager の MFA 済みセッションを要求する。店舗は staff で運用するため（2026-11-07 決定）、POS のサーバーアクション `recordStoreCashPayment` が店頭の前提（店頭の受付・査定確定・本人確認済み・署名済み・全額）を確かめたうえでサーバー権限で RPC を呼び、記録者（`order_payments.created_by`）と監査ログ（`store_cash_paid`、高額の印つき）を残す。高額取引（承認ライン以上）は画面で管理者への連絡を促すだけで、遠隔承認の手順は未実装。

## 3. 業務フロー

### 3.1 買取

```
受付 → 査定 → 査定結果の提示 → 本人確認 → 申込書兼受領書に署名 → 現金支払い → 明細印刷 → 在庫入庫（自動）→ 台帳確定（自動）
```

1. **受付**: 顧客を電話番号か氏名で検索、なければ新規。持込点数を入れて受付番号を発行する。受付票（番号と待ち人数）はレシートプリンタで印刷するので別の機械は要らない。混雑しない想定なら印刷は省略できる。SMS や LINE での呼び出し通知は v1 では作らず、開店後に様子を見て足す。
2. **査定**: 明細を作る。入力方法は 3 通り。
   - 価格表から型番・名前で検索して選ぶ
   - カードの写真から型番を読み取って候補を出し、店員が確定する（高額品向け）
   - まとめ買取: 「50 円 × 120 枚」のように価格帯と枚数だけ入れる（1 枚ずつは登録しない）
   状態ランクを選ぶと減額率が自動で掛かる。ランク外の個別減額は理由必須。PSA 鑑定品は既存の証明書番号入力を使う。
3. **査定結果の提示**: 合計を見せる。「持ち帰る」場合は査定のみで終了し、記録は残す（支払い・在庫・台帳には進まない）。
4. **本人確認**: 書類の種類を選び、表面を撮影（任意。保険証は撮影不可）。住所・氏名・生年月日・職業を入力。生年月日から年齢を自動判定し、**18 歳未満は保護者（親権者・未成年後見人）の同席が必要**。同じ画面で保護者の氏名・続柄（父／母／その他の親権者等）・本人確認書類（任意、表面のみ撮影可）を記録し、保護者本人に同意文への署名をしてもらうと進める。保護者が来ていなければ「お断り」として受付を終了する（電話での同意は不可）。保護者の情報は `store_identity_checks.guardian_*` に入り、DB の制約で 18 歳未満は氏名・続柄・署名が無いと保存できない（移行 20261108000002）。申込書 PDF に保護者欄と同意署名が載り、台帳の確認方法に「保護者同意あり（氏名）」が付く（2026-11-08 実装）。書類がない場合は紙に面前で手書きしてもらい、その紙を撮影する経路に切り替える。リピーターは前回の本人確認内容を呼び出して確認だけにする。撮影を標準にするかは再検討の約束あり。
5. **申込書兼受領書**: 明細、合計、誓約事項、個人情報の利用目的、本人確認の内容を 1 画面に表示し、署名してもらう。署名は 1 回で「査定額への同意」「誓約」「現金の受領」を兼ねる。署名時点の内容と署名画像を PDF（A4、サーバーで jsPDF + NotoSansJP）にして `store-documents` に保存する。文面は `AGREEMENT_TEMPLATE`（src/lib/pos-buyback.ts）で版管理する。
6. **現金支払い**: POS が支払額を大きく表示し、スタッフが金庫から現金を数えて渡す（キャッシュドロワーの連携はしない）。manager が金額を確認して記録（既存の `recordCashPaymentWithSignature` を流用）。レジの現金残が減る。一定額以上は manager の承認を必須にする（金額は未決）。
7. **明細印刷**: 買取明細書をレシートプリンタで印刷して渡す。同意書全文の客控えは法律上の義務がないので、明細書に要旨を載せ、希望者にのみ印刷する。
8. **在庫入庫**: 支払い完了をトリガーに明細ごとに在庫レコードを自動で作る。買取単価がそのまま仕入原価になる（手入力なし）。入った直後は「振分待ち」の状態で貯めておき、後から「店頭販売」か「本部へ移動」にまとめて振り分ける（6.7 節）。
9. **古物台帳**: 支払い完了時に台帳レコードを確定する（5.2 参照）。

### 3.2 販売

```
商品のスキャン or 検索 → カート → 合計（内税）→ 預り金・おつり → レシート印刷 → 在庫出庫
```

- 在庫ラベル（Code128）をスキャンしてカートに入れる。ラベルのない商品は検索で選ぶ。
- ラベルに価格は印字しないので、スタッフが値段を確認したいときは販売画面の「価格確認」でスキャンする。現在の売価・状態ランク・入庫日が表示され、カートには入らない。
- 安価カードは 1 枚ずつラベルを貼らず、「100 円カード」「300 円カード」などの価格帯バーコードをレジに置き、枚数で会計する。
- 預り金を入力するとおつりを大きく表示し、スタッフが金庫から数えて渡す。
- 消費税 10% の内税で計算し、レシートには税率ごとの合計と消費税額を載せる。適格請求書発行事業者なら登録番号も載せる。
- 返品はレシート番号から呼び出し、返金額を記録して在庫に戻す。
- 宛名付きの領収書を求められた場合は、販売の詳細画面から「領収書を発行」で印刷する。紙の領収書は 5 万円以上で収入印紙が必要なので、画面に案内を出す。

### 3.3 レジ

- 開局時に**その日のレジ担当者を選び**、釣銭準備金を入力する。店舗は 1 アカウントを共有するため、担当者名は管理画面の「検品者リスト」（共通）から選ぶ（管理者が遠隔で名前を足す）。交代はレジ画面の「担当を交代」で名前だけ替える（監査ログに履歴）。選んだ名前は査定確定の担当、申込書の立会、台帳の記録者名、明細書の担当に使う（2026-11-07 決定）。
- 入出金（釣銭補充、経費）を記録する。
- 閉局時に「理論残高 = 準備金 + 販売現金 − 買取支払い ± 入出金」と実際の現金を突合し、差額と理由を記録する。
- 日次レポート（買取件数・金額、販売件数・金額、粗利、現金差額）を管理画面で確認する。

## 5. データ設計

### 5.1 既存テーブルの再利用

- **orders / order_items**: 店頭買取もこのテーブルに入れる。`orders.channel`（`'online' | 'store'`）を追加し、店頭は配送系の列を使わない。
  - ステータスは既存値を使い、POS では表示名を読み替える（`申込` = 受付、`検品完了` = 査定確定、`振込済` = 支払済、`キャンセル` = 持ち帰り・取消）。新しいステータス値を足すと支払い系トリガーの改修が広がるため、v1 では値を増やさない。
  - `order_items` に `condition_rank`（状態ランク）、`price_band_id`（まとめ買取の価格帯）、`list_price`（ランク適用前の価格表の単価）、`deduction_reason` を追加する。
- **customers は使わない → store_customers を新設**（2026-11-07 実装時に変更）。既存の `customers` は `id` が `auth.users` を参照する会員アカウント専用で、アカウントを持たない来店客を入れられない。店頭客は `store_customers`（tenant_id、氏名、電話、住所、生年月日、職業、直近の本人確認書類、検索用に正規化した電話番号）に入れ、`orders.store_customer_id` で紐付ける。受付時に名前も電話も無ければ null のまま作り、本人確認で紐付ける。
- **注文番号**: 店頭は `ST-YYYYMMDD-NNN`（受付番号は末尾の NNN）。通販の `BB-` 採番は変えない。`orders.intake_count`（持込点数）、`intake_kind`（区分）を受付時に記録する。
- **注文行の作成**: RLS が admin / manager 限定なので、受付の作成だけサーバー側で管理クライアント（tenant_id 明示）を使い、明細と状態の更新は利用者のクライアント（RLS）で行う。
- **order_payments**: 現金支払いと受領サインはそのまま使う。
- **products**: 店舗テナント用の価格表。同期用に `source_product_id`（取り込み元の商品 ID）、`price_locked`（店舗で手動調整したら true、以後同期で上書きしない）、`store_only`（店舗専用。同期で消えない）、`standard_sale_price`（標準売価。在庫に売価を付けるときの初期値。状態ランクごとの率を掛ける）を追加する。
- **security_audit_events**: 支払い・取消・台帳確定・在庫調整・価格ロックの監査に使う。

### 5.2 新規テーブル

すべて `tenant_id` を持ち、既存と同じ方針で RLS を付ける（staff は読み取り可、manager / admin の書き込み系は MFA 必須に揃える）。

**condition_ranks（状態ランク表）**

| 列 | 内容 |
|---|---|
| code, label | A / 美品 など |
| rate | 減額率（1.00、0.80、0.50 …） |
| description, sample_image_path | 見本と説明。通販用の品質ガイドの写真を流用する |
| sort_order, is_active | |

**store_identity_checks（店頭の本人確認）**

| 列 | 内容 |
|---|---|
| order_id | 対象の買取 |
| customer_id | リピーター呼び出し用 |
| method | `id_document` / `handwritten` |
| document_type | 運転免許証、マイナンバーカード、パスポート、在留カード、健康保険証、その他 |
| name, address, birth_date, occupation | 確認した内容（台帳に転記する） |
| age_at_check | 確認時点の年齢（自動計算） |
| front_image_path | 表面の画像（任意。裏面は保存しない） |
| handwritten_image_path | 手書き文書の画像（`method = handwritten` のとき必須） |
| guardian_name, guardian_relation, guardian_document_type, guardian_image_path, guardian_signature_path | 18 歳未満の保護者同意（`age_at_check < 18` のとき必須） |
| verified_by, verified_at | 確認した店員と時刻 |
| revoked_at, revoked_by, revoke_reason | 取消 |

既存の `order_paper_kyc` は振込口座の照合が前提なので流用しない。

**store_agreements（申込書兼受領書）**

| 列 | 内容 |
|---|---|
| order_id | 対象の買取 |
| template_version | 誓約文のバージョン |
| content_snapshot | 署名時点の明細・合計・本人確認内容（jsonb） |
| signature_path | 署名画像 |
| pdf_path | 生成した PDF |
| signed_at | 署名時刻 |

**kobutsu_ledger（古物台帳）**

| 列 | 内容 |
|---|---|
| order_id または sale_id | 買受か売却か |
| transaction_type | `purchase` / `sale` |
| transacted_on | 取引年月日 |
| items | 品目・数量・特徴（jsonb。商品名、型番、状態ランク、PSA 番号） |
| counterparty_name, counterparty_address, counterparty_occupation, counterparty_age | 相手方 |
| identity_method | 確認方法（書類種類、または面前手書き） |
| recorded_by, recorded_at | 記録者 |

支払い完了時に確定し、以後は更新しない（追記のみ。DB トリガーで UPDATE / DELETE を全員に禁止し、INSERT はサーバーだけ。2026-11-07 実装）。3 年保存。売却側はトレカが記録義務の対象外なので v1 では買受のみ書く。CSV と PDF で出力できるようにする。

台帳と取引履歴は別物。取引履歴（買取一覧・販売一覧・顧客ごとの来店履歴）は日々の操作用で、そこから再印刷・取消・返品を行う。台帳は法律で義務付けられた記録で、取引履歴から自動で作られる変更不可のコピーと位置づける。

**inventory_items（在庫）**

| 列 | 内容 |
|---|---|
| product_id | 価格表の商品（null 可。自由入力品に対応） |
| name, model_number | 表示名と型番 |
| condition_rank | 状態ランク |
| psa_cert_number | 鑑定番号（あれば） |
| barcode | ラベル用の識別子（Code128。レコード ID を元に生成。価格は印字しない） |
| source | 入庫元（`buyback` 買取 / `opened_box` 開封 / `transfer_in` 本部から入庫 / `manual` 手入力） |
| source_order_item_id, source_lot_id, source_transfer_id | 入庫元の買取明細、開封した仕入ロット、または本部からの移動伝票 |
| cost | 仕入単価（買取単価、開封時の按分単価、または本部から入庫したときの原価） |
| sale_price | 売価（未設定なら販売不可。相場価格を参考表示） |
| quantity | 同一商品の数量（高額品は 1 件 1 枚。境界は未決） |
| allocation | `pending`（振分待ち） / `store`（店頭販売） / `transfer`（本部へ移動） |
| status | `in_stock` / `sold` / `reserved` / `written_off` / `transferred` |

**purchase_lots（仕入ロット: ボックス・パック）**: 商品名、仕入先、数量、仕入値合計、仕入日、開封日、按分方式（`equal` 均等 / `market` 相場比例）、開封で登録した在庫の件数。

**price_bands（価格帯）**: 安価カードのまとめ買取・販売用。`label`、`buy_price`、`sell_price`、`barcode`。

**inventory_movements（入出庫履歴）**: inventory_item_id、種別（`in` / `sale` / `return` / `adjust` / `transfer` / `stocktake`）、数量、関連する注文・販売・移動伝票 ID、理由、操作者。

**inventory_transfers（本部との移動伝票）**: 方向（`out` 店舗→本部 / `in` 本部→店舗）、相手（通販テナント）、明細（商品、数量、原価）、送付日、受入日、作成者。店舗→本部は店舗の在庫から消え、店舗の粗利には乗せず原価で振り替える。本部→店舗は受け入れた時点で店舗の在庫になり、伝票の原価が仕入単価になる。通販側には在庫機能がないので、本部側の記録は伝票だけで追う。

**stocktakes / stocktake_lines（棚卸し）**: 実施日、担当、行ごとの理論在庫数・実数・差異・理由、確定時刻。

**sales / sale_items（販売）**

- sales: sale_number、subtotal、tax_amount、total、tendered（預り金）、change（おつり）、register_session_id、sold_by、voided_at、void_reason
- sale_items: inventory_item_id または price_band_id、quantity、unit_price（税込）、tax_rate

**register_sessions / cash_movements（レジ）**

- register_sessions: opened_at、opened_by、opening_float、closed_at、closed_by、expected_cash、counted_cash、difference、notes
- cash_movements: register_session_id、種別（`in` / `out`）、金額、理由、操作者

**purchase_refusals（買取拒否の記録）**: customer_id、理由（偽造の疑い、本人確認不可、未成年など）、記録者。

### 5.3 ストレージ

非公開バケット `store-documents` を追加し、`{tenant_id}/{order_id}/...` の階層で本人確認画像、手書き文書、署名、申込書 PDF を保存する。既存の `cash-receipts` バケットの署名はそのまま使う。保存期間は台帳と同じ 3 年を基本とし、cron で期限切れを削除する（既存の `cleanup-kyc` と同じ方式）。日次バックアップに店舗テーブルを含める。

## 6. 価格表と在庫の考え方

- **価格表（買取対象マスタ）と在庫（実物）は別物**。価格表は通販から同期したものに店舗専用の商品を足せる。在庫は買取から自動生成され、手入力は例外（持込以外の仕入れ、棚卸の発見）だけ。
- 査定時に価格表にないカードは自由入力で明細にでき、その場でのマスタ登録は不要。あとから「マスタに登録」できる。

### 6.1 価格同期（通販 → 店舗）

- 同じ DB 内なので SQL 関数 `sync_store_prices(source_tenant, target_tenant)` で行う。カテゴリ・サブカテゴリ・商品を `source_product_id` をキーに upsert する。
- 取り込み時に店舗係数 `store_price_rate` を掛ける。
- `price_locked = true` の商品は価格を上書きしない（名前・型番・画像などは追従する）。商品画面で価格を直接直すとロックが立ち、「同期に戻す」で解除。商品一覧に「調整済み」の絞り込みを付ける。
- 実行は自動を基本にする。毎日、設定した時刻（既定は深夜）に cron が動く。通販側の価格更新のタイミングと合わないときは、設定タブの「今すぐ同期」で手動実行できる。最終同期の日時と件数を設定タブに表示する。
- 新商品の登録・編集は通販側で行い、同期で店舗に流れる。通販側の商品マスタは別の開発者の領域なので、こちらは読むだけにする。
- 千葉向けの既存同期（`src/app/api/sync-prices-to-chiba/route.ts`）は別プロジェクト宛てなので触らない。

### 6.2 ラベルと価格の見せ方

- ラベルには在庫 ID のバーコードと商品名だけを印字し、価格は印字しない。スキャン時点の売価で会計するので、値下げしても貼り替え不要。
- 店頭で価格を見せたい高額品はケース用のプライスカードを別に印刷し、そちらだけ差し替える。
- **客向けの売価表示は電子棚札ではなく、iPad の客向け表示か QR コードの価格ページで行う。** 電子棚札は本体 1 枚 1,000〜3,000 円に受信機 2〜20 万円と連携開発が要り、100 枚規模で 20〜40 万円超になるため見送る。ラベルに価格を印字しないので、相場が変わっても貼り替えは発生しない。
- バーコードが要るのは販売と棚卸のときだけ。買取では使わない。
- バーコードは必須ではない。無くても在庫番号や商品名の検索で販売できる。価値は販売のスピード、似たカードの取り違え防止、棚卸しの速さ。開店当初は高額品だけラベルを貼り、安価カードは価格帯で会計する。リーダーは後から足せる。
- **安価カードの価格帯はスリーブの色で識別する。** 価格帯カードはシステム上「100 円帯 320 枚」のように枚数だけ持ち、どのカードがどの帯かは記録しない。置き場所（箱の仕切り）だけで管理すると客が戻し間違えたときに価格が分からなくなるので、価格帯ごとにスリーブの色を決める（例: 100 円は透明、300 円は青、500 円は赤）。レジでも棚でも一目で帯が分かり、コストはスリーブ代だけで再印刷も要らない。色と価格帯の対応表はレジ横に掲示し、設定タブの価格帯一覧にも色を登録する。

### 6.3 価格の入力・調整場所（POS の「価格表」タブ）

価格は POS の「価格表」タブに集約する（管理画面の価格表と同じ内容）。商品 1 行に次の 3 つの価格を並べる。

| 価格 | 入るタイミング | 直す場所 |
|---|---|---|
| 通販の買取価格 | 同期で自動 | 直せない（通販側で変える） |
| 店舗の買取価格 | 同期時に係数を掛けて自動。例: 係数 95% なら通販 16,000 円 → 店舗 15,200 円 | 価格表タブで商品ごとに上書き。上書きした商品は「調整済み」になり同期で変わらない。「同期に戻す」で解除 |
| 標準売価 | 店舗で入力（任意。相場価格を参考表示） | 価格表タブ。状態ランクごとの率を掛けて在庫の売価の初期値になる |

- 一律の係数はテナント設定（設定タブ）で変える。係数を何%にするかは未決で、95% は判断材料としての例。
- 在庫 1 件ごとの売価は、標準売価 × ランク率を初期値として在庫画面で上書きできる（同じ商品・同じ状態をまとめて値下げする一括操作も付ける）。
- 店舗専用の商品（通販で扱わない物）は価格表タブから追加でき、同期で消えない。

### 6.4 棚卸し

現場の負担を減らすため「理論在庫と実数の突合」を基本にする。棚卸しモードで、システムが商品ごと（安価カードは価格帯ごと）の理論在庫数を一覧で出し、現場は実数を入力するだけ。差があった行だけ理由を入れて確定し、在庫を実数に合わせる。高額品はラベルのスキャンでも確認済みにできるが、必須ではない。理論在庫が正しいかは販売・移動の登録漏れがないかにかかるので、移動は必ず伝票を切る。頻度は月 1 回か四半期ごとが目安。

### 6.5 本部（通販側）との在庫移動

- **店舗 → 本部**: 出庫区分「本部へ移動」で店舗の在庫から外し、移動伝票を残す。
- **本部 → 店舗（事務所からの仕入れ）**: 通販側で買い取った物を店舗で売る場合。「本部から入庫」で伝票（商品、数量、原価）を登録して受け入れると店舗の在庫になり、伝票の原価が仕入単価になる。本部側で古物台帳の記録は済んでいるので、店舗側で台帳は書かない。
- 店舗と通販は同じ法人なので、どちらの方向も社内の振替で済み、売買にはならず台帳にも載せない。

### 6.6 開封入庫（ボックス・パックを開けて在庫にする）

仕入ロット（ボックス 1 個、仕入値、仕入先）を登録し、開封して出たカードを枚数で登録すると、1 枚あたりの仕入単価を按分する。按分は「均等割り」と「相場に比例して高額カードに多く配分」の 2 方式を選べる。どちらが税務上よいかは税理士に確認する。問屋から新品で仕入れたボックスの開封品は古物営業法上の古物ではないので台帳は不要。個人からボックスを買い取った場合は古物として扱う。

### 6.7 振分待ち

買取で入った在庫は自動的に「振分待ち」になる（本部から入庫した物は売る前提なので最初から店頭販売）。在庫画面の「振分待ち」タブで、店頭販売に回す物と本部へ移動する物をまとめて選び、移動分は 1 枚の移動伝票にする。週 1 回まとめて送る運用に向く。 店頭販売に回す物は「個別管理（ラベルを貼る）」か「価格帯（どの帯か）」をここで選ぶ。価格帯を選んだ物は個体の記録をやめて帯の枚数に加算し、その帯の色のスリーブに入れ替える。

## 7. 査定を楽にする仕組み

- 型番検索を最優先にし、名前の部分一致は補助にする。
- カードの写真から型番を読み取り、価格表の候補を出す（既存の AI 解析基盤を使う。精度は 100% ではないので店員が確定する）。
- 「最近査定した商品」を先頭に出す。
- 査定画面の横に相場価格（通販で取得している相場データ）を表示する。
- 状態ランクはボタンで選び、減額率は自動で掛ける。同じカードで状態が混ざる場合は明細をランクごとに分ける。
- まとめ買取は価格帯 × 枚数。枚数は手で数えるのを基本とし、はかり（1 枚およそ 1.7 g）での概算は任意。

## 8. 帳票

### 買取明細書（客に渡す）

- 店名、住所、電話、古物商許可番号
- 日時、取引番号、担当者
- 明細（商品名、型番、状態ランク、数量、単価、金額）、減額、合計
- 支払方法「現金」、本人確認済みの旨
- 注意書き（買取成立後の返品不可、署名済みの旨）。店頭買取はクーリングオフの対象外

### 販売レシート

- 返品条件

### 申込書兼受領書 PDF（店が保管）

- 明細・合計・誓約事項・個人情報の利用目的・本人確認の内容・署名画像・署名時刻

- 宛名、但し書き、金額、日付、店舗情報、登録番号。5 万円以上は収入印紙の案内を表示

## 10. 法令対応の対応表

| 要件 | 根拠 | システムでの対応 |
|---|---|---|
| 相手方の住所・氏名・職業・年齢の確認 | 古物営業法 15 条、施行規則 15 条 | 本人確認画面で必須入力。全件実施（金額による免除は使わない） |
| 身分証がない人への確認 | 施行規則 15 条（面前での手書き文書） | 手書き経路。iPad に住所・氏名・職業・年齢を面前で書かせ画像保存 |
| 取引記録の作成・3 年保存 | 古物営業法 16 条・18 条 | `kobutsu_ledger` に支払い時に確定。追記のみ。CSV / PDF 出力 |
| 18 歳未満からの買取禁止（保護者同意を除く） | 山口県青少年健全育成条例 10 条 | 生年月日から判定し、保護者同意（同席した保護者の氏名・続柄・同意署名）の記録がなければ進めない。DB 制約でも強制 |
| マイナンバーの収集禁止 | 番号法 | 裏面は撮影不可と画面に明示。表面のみ保存 |
| 個人情報の利用目的 | 個人情報保護法 | 申込書に明記し、同意の署名を取る |
| 販売時の消費税・インボイス | 消費税法 | レシートに税率別合計・消費税額、登録番号（登録している場合） |
| 買取の仕入税額控除（古物商特例） | 消費税法 | 台帳に相手方の住所氏名と取引内容が残るので要件を満たす |

システム外で必要な手続き: 営業所新設の届出（山口県公安委員会、事前届出）、店舗への標識掲示、営業所の管理者の選任、インボイス登録の要否の判断と現金売上の記帳方法の確認（税理士）、プライバシーポリシーへの店頭買取の記載追加。

## 11. 運用上の考慮

- **通信断**: 紙で受付と本人確認を取り、復旧後に入力する手順を決める。POS はオフライン動作を作らない。
- **高額取引の決裁**: 一定額以上は manager の承認を必須にする（金額は未決）。
- **同一人物の履歴**: 短期間に何度も持ち込む人を顧客画面ですぐ確認できる。
- **偽造・改造カードの疑い**: 買取拒否を理由付きで記録する。
- **端末のセキュリティ**: 待機画面には金額を出さない（客の目に入る前提）。画面ロック、離席時の自動ログアウト、iPad 紛失時にアカウントを止める手順（既存のスタッフ無効化を使う）。
- **安価カードの価格帯の識別**: スリーブの色で価格帯を表す（6.2 節）。振分待ちから店頭販売に回すときに価格帯を選び、その色のスリーブに入れ替えてから箱に入れる。価格帯を変える（値下げする）ときはスリーブも入れ替える。色と帯の対応を変えるときは全入れ替えになるので、開店前に決めて以後は変えない。迷ったら POS の価格表で商品名を検索して標準売価を見る。
- **機器故障**: 帳票の再印刷。
- **記録の保持と削除**: 台帳と本人確認画像を 3 年保存し、期限後に自動削除。

## 12. 実装の段階分け

| 段階 | 内容 | 開店までに必要か |
|---|---|---|
| 0 | テナント作成、`mode` / `cash_only` 追加、PWA の殻、店舗モードでの公開ページ非表示 | 必要 |
| 1 | 買取 POS 一式（受付〜査定〜本人確認〜申込書〜現金払い〜明細印刷〜台帳）、状態ランク表、レジ開閉 | 必要 |
| 2 | 在庫（入庫・売価・ラベル）と販売（会計・価格帯・レシート・返品） | 販売を初日から行うなら必要 |
| 3 | 価格同期、写真からの型番読み取り、日次レポート、棚卸、ストレージの期限削除 | 開店後でも可（価格同期は初期投入を手動で代替できる） |

段階 1 と 2 は独立して進められる。段階 1 を先に本番（店舗テナントのみ）に出し、店舗で試しながら段階 2 を仕上げる。

確認の進め方: 設計段階はクリックできるモックアップ（非公開 URL）、実装段階はローカルの開発サーバー（同じ Wi-Fi の iPad から実機確認）、開店前は本番の店舗テナント（URL 公表前は実質下書き）。

## 14. 深める論点（実装前に会話で詰める）

1. **買取の流れ**。受付票を出して待ってもらうのか、その場で査定するのか。減額時の同意の取り方。持ち帰った客の査定結果を再来店時に呼び出すか。
2. **本人確認の運用**。撮影を標準にするか目視にするか。手書き経路と保護者同意の画面を開店当初から作るか、当初は「断る」運用で後回しにするか。
3. **在庫と販売**。1 枚 1 件で管理する境界（金額か、PSA 品か）。売価の決め方。インボイス登録の有無。
4. **レジ締めと数字**。日次で見たい項目。月次集計や会計ソフト（既存の MF 連携を含む）への受け渡し。
5. **現金支払いの権限**（決着 2026-11-07）。店舗は staff で運用し、staff が支払いの記録とレジ締めまで行う。管理者は遠隔で、設定・ランク表・価格帯・台帳 CSV を持つ。残り: 高額取引の承認ライン（金額）と遠隔承認の手順。
6. **既存の通販との関係**（決着）。同じ人が兼ねる。開店時はテナントごとに 1 アカウントずつ持ち、不便なら 1 アカウントでテナントを切り替える仕組みを後から足す。
