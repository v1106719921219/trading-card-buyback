# セキュリティ修正第2段階の導入手順

この変更にはDB移行とアプリの両方が必要。コードだけをデプロイしないこと。
東京・山口と千葉は別Supabase。各環境の鍵・テナントを混用しない。

1. バックアップの実成功・復元方法と、Supabase管理者がMFA紛失時に本人確認して復旧できることを確認する。実顧客を使う復元試験はしない。
2. 管理者・マネージャーへ、次回ログインに認証アプリの登録／コードが必要になることを案内する。現時点では全員の登録完了は未確認。
3. 短いメンテナンス時間を確保し、両DBに `20260913000002` → `20260913000003` → `20260913000004` の順でSQLを適用する。MFA制限がDB側で有効になり、旧画面の管理者操作が一時的に制限される。
4. 各環境のサーバー専用環境変数を安全な方法でプロセスに渡し、`SECURITY_TENANT_SLUG=quadra` または `chiba` として `node scripts/security/migrate-mf-tokens.cjs --stage` を実行する。必要な変数は `NEXT_PUBLIC_SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、その環境の `ORDER_ACCESS_SECRET`。値をコマンドやログに貼り付けない。既存MF連携を暗号化列に準備し、旧コード用の列はこの段階のみ残す。連携0件は正常。
5. セキュリティ修正だけのブランチを両Vercelプロジェクトへデプロイする。未公開のX投稿セット変更は含めない。READYと両ドメインのログイン・申込・管理者の二段階認証導線を確認する。
6. 各環境で上記スクリプトを `--finalize`、続いて `--check` で実行する。旧列の平文が0件、既存連携がすべて復号検証できることを確認する。同時更新検出時は上書きせず再確認する。移行中の旧デプロイへのアクセスを残さない。
7. 未認証での管理API拒否、他テナント拒否、既存スタッフの検品可否、管理者のMFA後操作を確認する。実送信・振込・本注文作成は業務担当者のテスト時のみ。

## アカウント停止・MFA復旧

退職時は管理者がスタッフ管理で「利用を停止」。プロフィールは残り、既存JWTでもRLSによる業務データアクセスを拒否する。別途Supabase Authで該当者のセッション失効／ログイン禁止を実施し、共有パスワードがあれば変更する。実在アカウントの停止・一覧棚卸しは今回実施していない。
MFA端末紛失時は、管理者が別経路で本人確認してからSupabase管理画面で対象要素だけをリセットする。アプリ全体のMFAを解除しない。

## ロールバックの注意

MF暗号化の完了後に旧コードへ戻すと会計連携が使えない。暗号化対応済みコードを維持して修正する。RLS／MFAを一括解除するロールバックは行わない。価格署名導入後、以前開いていた申込画面は再読み込みが必要。旧LINE署名リンクは失効し、新リンクまたはLIFFで本人確認する。

## 既知の運用上の限界

- LINE Webhookは重複を記録して一度だけ処理する。途中失敗・結果不明時は自動再送せず、運用者が状況を確認する。
- AI本人確認は厳格な形式検証と費用回数上限を追加したが、AI判定そのものの正確性を保証しない。
- 回数上限は共有DBで実施。大量の分散IP攻撃へのWAF、Supabase Auth自体の制限、Sentry通知、Drive共有設定、バックアップ復元は別途運用確認が必要。
- DBの会計トークン暗号化後も、過去バックアップから平文を消すものではない。保管権限・保存期限を別途管理する。

## 検証

`npm run test:security`（架空データのみの25件）、`npm run build`、`npm audit`。
両DBのSQLはトランザクション内で適用後ROLLBACKする検証に成功。永続適用とは区別する。
Proxyはsrc/appと同階層のsrc/proxy.tsに配置する。[Next.js公式](https://nextjs.org/docs/app/api-reference/file-conventions/proxy)。
